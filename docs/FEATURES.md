## Layer 0 — Personalisation and assessment setup

### `profile.cv_extraction` — CV to skill knowledge graph

**stub** · owner: shared · blocked on: Real participants. The metric is defined as a comparison against
a participant-approved graph, and zero participants have reviewed one. Nothing
here is measurable at build time by construction — a synthetic CV compared
against a synthetic approval measures the fixture.

**What we take.** A deterministic, sectioned, dictionary-and-pattern extractor. Reads a
PDF, DOCX or TXT into text, finds the conventional CV sections, and proposes
Skill / Project / Experience / Education / Certification nodes with a
provenance (which section) and a confidence.

Node types and relations are closed vocabularies (profile/schema.py). Machine
suggestions live in `extracted` and participant-confirmed claims live in
`approved`, as separate fields — not one list with a flag.

**What we change.** The extraction itself is deliberately NOT a language model — see
"LLM-assisted cleanup" below for the one narrow, optional exception. This
project has a recorded negative result on asking a generative model to
describe an input it was given (docs/removed-emotion-monitor.md: evidence
absent from the input asserted in 42 of 50 cases). A model that invents a
skill from a CV produces a claim about a person's employment history with
nothing behind it, and this feature's own metric — node precision against the
participant-approved graph — would then be measuring hallucination rate under
a different name.

Checked against a second codebase in this repository (`KG/`), which builds a
fuller resume graph using exactly the declined architecture — NVIDIA NIM LLM
extraction plus a spaCy NER cross-check — and confirmed the decision rather
than reopening it: `KG/`'s LLM pass sends each candidate's full CV text to a
third-party API, the same privacy shape as the emotion monitor this project
already removed for the analogous reason.

One piece of `KG/` WAS adopted (2026-08-20): `profile/esco.py`, an optional
second skill matcher tried only on Skills-section items the hand-typed
dictionary misses. It runs local sentence-transformer embeddings against a
bundled copy of the public ESCO taxonomy (~13,900 occupational/soft-skill
concepts) — no CV content leaves the machine, no third party, no LLM. Off by
default (`PP_ESCO_SKILL_MATCHING` unset); every test in the suite runs without
it and without `sentence-transformers` installed. It does not replace the
dictionary — ESCO has little fine-grained tech vocabulary, so at a threshold
loose enough to catch genuine soft-skill matches it also catches spurious tech
ones (documented false attractors ported from `KG/`'s own tuning, e.g. "numpy"
scoring above "numerology"). The two are complementary: dictionary first
(precise, tech-focused), ESCO second (broad, occupational/soft-skill).

The recall cost is real and is why the metric counts what participants had to
add by hand. A skill that appears in no recognised section, names no known
technology, and clears no ESCO threshold is missed.

The confidences are stated priors per extraction route, not fitted
probabilities. `ExtractionReport.confidence_provenance` says
`stated-priors-not-fitted` so a reader cannot mistake them for measurements. An
ESCO-accepted match additionally carries a genuinely MEASURED cosine
similarity (`esco_similarity`), kept as a separate field rather than folded
into the prior — the two answer different questions and conflating them would
misreport both.

LLM-assisted cleanup (2026-08-20) — the ONE tier that leaves the machine, and
the one exception to "not a language model" above. `profile/llm_cleanup.py`,
tried third, only on Skills-section items that miss BOTH the dictionary and
ESCO. Sends NVIDIA NIM only the isolated skill phrase itself — never CV prose,
never a name, employer, or date — a materially narrower disclosure than `KG/`'s
full-document LLM pass, confirmed explicitly with the user before being built
given they had already declined the fuller version for the same privacy
reason. Off by default (`PP_NIM_SKILL_CLEANUP` unset); every test in the suite
supplies an injected fake call function, so the suite needs no network access
or API key.

A correction is never trusted on the model's say-so: `clean_batch` runs every
proposal through a similarity guard (stdlib `difflib`) before accepting it — a
typo fix keeps the string close to the original, a model that quietly
substitutes a different skill ("Go" -> "Google") does not, and is rejected
back to the raw text. This is the same hallucination risk the opening
paragraph describes, scoped down and guarded rather than eliminated, which is
why it stays a last-resort tier rather than the default path. An accepted
correction carries the original alongside it (`cleanup_original`), the same
shape `schema.approve` uses for a participant's own edits, so a reviewer can
always see what was replaced — and, like everything else this module
produces, it is still just an unapproved suggestion until a person confirms
it.

**Validating metric.** node-level precision and recall against the participant-approved
graph; proportion of extracted nodes edited or removed; all broken out by
provenance section, so a bad section is identifiable rather than averaged
away. For the LLM cleanup tier specifically: acceptance rate against the
similarity guard, and — once real corrections exist to review — the rate at
which a participant keeps vs. reverts an accepted correction, which is the
actual measure of whether the guard's threshold is set well

**Gate.** precision >= 0.80 and recall >= 0.70 on real participant CVs, with the edited-or-removed proportion reported alongside

**The interface may say.** "Skills read from your CV. Nothing here is a claim about you until you approve it."

### `assessment.question_generation` — Question and rubric generation

**stub** · owner: shared · blocked on: Real participants and blinded expert raters. Every part of this
gate is a human judgement about questions generated for real people from real
approved graphs, and neither exists yet.

**What we take.** Versioned question families. A family fixes target competency,
difficulty definition per tier, duration range, required deliverables and
rubric dimensions; the scenario adapts to the participant's approved skills.
The family key (`id@vN`) is stored on question.json, which is what makes two
sessions comparable at all.

Difficulty tiers T1-T4 and the domain tracks come from Main_Idea's Problem
Library Architecture. Every family declares all seven of Main_Idea's problem
validity properties and `validate_family` refuses one that does not.

The rubric is generated alongside the question and stored with it, because the
blind quality raters score against it and a rubric regenerated later is a
different rubric.

**What we change.** **Template-based, not LLM-generated.** `.env` configures no
provider and `default_generator()` returns the deterministic
`TemplateGenerator`. That is the shipped behaviour, not a degraded mode. A
`ProviderGenerator` and a `QuestionGenerator` protocol exist so the boundary is
swappable and every test runs offline, and no provider client is wired: doing
so is a change somebody makes knowingly, in a commit that also edits this
entry.

The known weakness is exactly what `inter_question_similarity` in the gate
below measures. The template cannot invent a novel situation, so two
participants at the same tier in the same family see the same frame with their
own skills in it. The family already fixes competency, difficulty,
deliverables and rubric — which is most of what makes a question valid — so
this is a real question, not a placeholder. How much the missing variation
costs is a measurement nobody has taken.

The generator payload is built as an allowlist, field by field, and excludes
unapproved nodes, CV prose and personal identifiers.
`tests/test_generator_payload_is_clean.py` inspects the outgoing payload
itself.

**Validating metric.** blinded expert ratings of skill relevance, difficulty agreement,
feasibility within the selected duration, and rubric completeness; plus
inter-question similarity within a family across participants

**Gate.** blinded raters agree the question targets the selected skills and matches the stated tier on >= 80% of generated questions, with inter-question similarity low enough that two participants are not effectively answering the same question

**The interface may say.** "Your question is built from the skills you approved, in a fixed family so sessions stay comparable."

## Layer 1 — Capture

### `capture.webcam_signals` — Webcam signal extraction (Extractor A)

**synthetic** · owner: Galib · blocked on: real sessions

- *constraint*: Barrett, Adolphs, Marsella, Martinez, Pollak (2019). Emotional Expressions Reconsidered (Psychological Science in the Public Interest 20(1))  ← venue unverified
- *tool*: Lugaresi et al. (2019). MediaPipe: A Framework for Building Perception Pipelines (arXiv / CVPR Workshops)  ← venue unverified

**What we take.** MediaPipe Face Landmarker (478-pt mesh with iris, plus the facial
transform matrix) to emit blink_rate_hz, ear_mean, ear_std, gaze_dispersion,
gaze_screen_fraction, head_pose_stability, motion_energy at 5 Hz.

**What we change.** No affect inference of any kind. Barrett et al. is the reason:
facial configuration to internal state does not survive review, and consumer
webcam conditions are worse than the lab conditions that review covers. Low-level
signals go out and the segmentation model learns whatever mapping exists.

**Validating metric.** face_valid_fraction per session; signal drop-out rate under real lighting

**Gate.** face_valid_fraction >= 0.85 on pilot sessions

**The interface may say.** "Behavioural signals extracted on-device. No inference about emotion."

### `capture.latent_encoder` — On-device latent encoder (Extractor B)

**spec** · owner: Galib · blocked on: real sessions; GPU budget

- *method*: Assran et al. (2023). Self-Supervised Learning from Images with a Joint-Embedding Predictive Architecture (I-JEPA) (CVPR 2023)
- *checkpoint*: Bardes et al. (2024). V-JEPA: Revisiting Feature Prediction for Learning Visual Representations from Video (arXiv / OpenReview — not a target venue)

**What we take.** Joint-embedding predictive architecture: predict masked-region
representations in latent space rather than reconstructing pixels. Emits
latent_0..latent_63 alongside the MediaPipe features. Raw video never leaves
the machine.

**What we change.** I-JEPA is the confirmed-venue anchor; the video variant is what
actually runs and has not cleared the venue bar. Cite the image paper for the
method, the video paper for the checkpoint, and say so plainly.

**Validating metric.** downstream segmentation F1 with latents vs MediaPipe features alone

**Gate.** latents add >= 3 F1@25 over MediaPipe-only, or they are cut

**The interface may say.** "Facial dynamics are encoded locally into a 64-dimensional vector."

### `capture.event_log` — Structured event log

**synthetic** · owner: Amatul · blocked on: hand annotation pass; a decision on whether the desktop agent is part of the protocol at all

- *schema*: Price, Hovemeyer, Rivers et al. (2020). ProgSnap2: A Flexible Format for Programming Process Data (ITiCSE 2020)  ← venue unverified

**What we take.** ProgSnap2 as the base schema for programming-process events, extended
with an AI-interaction taxonomy. Of the six declared AI event types, exactly one
is produced by a running component today: verification_action, emitted in-process
by the exam page. ai_session_open/ai_session_close have code but require a
desktop agent no participant is instructed to launch. ai_output_accepted has code
with no call site that raises on its own success path. prompt_submit and
response_received are declared and then actively refused by the schema
(UNCAPTURED_TYPES; a source="inferred" value raises), because inferring them
would mean fabricating them.

**What we change.** The AI taxonomy is the extension and does not exist in ProgSnap2,
Blackbox, or any prior corpus. Timing and counts only. Prompt text, response
text and keystroke content are discarded at the callback and never buffered.
The schema's refusal to accept inferred prompt_submit/response_received is the
design working as intended, not a gap: those two are unobservable without
content-script DOM access to a third-party AI site, and the honest encoding of
an unobservable event is its absence.

**Validating metric.** per-event-type precision/recall against hand annotation of 5 sessions

**Gate.** precision and recall >= 0.90 per event type that a running component can actually emit

**The interface may say.** "Timing and frequency of actions. No text, keystrokes or file contents."

### `capture.keyframe_reduction` — Screen keyframe reduction

**spec** · owner: Amatul · blocked on: implementation — screen_recorder.py currently writes a continuous MP4 with no reduction step

- *method*: Arefeen et al. FrameHopper: Selective Processing of Video Frames in Detection-driven Real-Time Video Analytics (check before citing)  ← venue unverified

**What we take.** Perceptual-hash redundancy skipping: drop frames whose Hamming
distance from the last kept frame is below threshold, keep a timestamp index.

**What we change.** Screen recordings are far more static than the natural video the
method was designed for, so the expected compression ratio is 20-50x rather than
the single-digit gains reported on natural video. Report the ratio as a result.

**Validating metric.** keyframes kept / total frames; human reviewability of the kept set

**Gate.** reduction >= 10x with no reviewer-reported loss of context

**The interface may say.** "Screen recording stored as keyframes for human review."

### `capture.clock_sync` — Dual-stream clock synchronisation

**stub** · owner: shared · blocked on: A measurement. The detector, the residual arithmetic and the
refusal are implemented and tested (analysis/clock_sync.py,
tests/test_clock_sync.py, including against encoded video), and the exam page
paints the flash and logs its session time. What does not exist is a single
session recorded with it: zero sessions on disk carry a clock_sync_flash event,
so the residual distribution the gate is stated over has no samples. Status
stays `stub` — an implementation is not a measurement.

Second, unmeasured question: whether a webcam in an ordinarily-lit room
registers a monitor flash at all. `find_flash` returns None rather than a guess
when it does not, so the failure mode is a refused session rather than a wrong
number, but the detection rate is unknown until sessions exist.

**What we take.** Nothing. One monotonic session clock, per-recorder offset in the manifest.

**What we change.** Validated by a clapperboard test every session. Two corrections to
how that was written here, both made after reading the code rather than the
plan.

The clap is dropped. `getDisplayMedia` is requested with `audio: false`, so the
screen recording has no audio track and a clap lands in exactly one of the two
streams. It would synchronise nothing, and asking a participant to perform one
would be a ritual. The check is the full-screen white flash only: the screen
recording sees it directly, the webcam sees the room brighten.

A scalar `clock_offsets.webcam_ms` cannot describe the webcam stream. The
webcam MediaRecorder pauses when the exam clock pauses; the screen recorder
does not and must not (invariant 2, Frontend Spec 8.1 rule 5). Webcam media
time therefore omits every paused span, and the map to session time steps at
each pause. The field is now null and `stream_timebases.webcam` carries the
piecewise map. It previously held 0 on every session, which on a session with a
90-second pause was wrong by 90,000 ms and indistinguishable from a
measurement.

Above 100 ms the session is refused for fusion by
`analysis.feature_assembly.session_readiness`, and so is a session whose
residual was never measured at all.

**Validating metric.** residual offset distribution across sessions

**Gate.** < 100 ms on >= 95% of sessions

**The interface may say.** "Streams are timestamp-aligned."

### `privacy.invertibility` — Latent invertibility experiment

**spec** · owner: Galib · blocked on: capture.latent_encoder

- *attack*: Fredrikson, Jha, Ristenpart (2015). Model Inversion Attacks that Exploit Confidence Information (ACM CCS 2015)  ← venue unverified
- *attack*: Dosovitskiy & Brox (2016). Inverting Visual Representations with Convolutional Networks (CVPR 2016)  ← venue unverified

**What we take.** Model inversion as the attack construction, feature inversion for
reconstructing an input from a representation, a face-recognition embedding
model as the identity oracle, LPIPS for perceptual distance on any
reconstruction.

**What we change.** The threat model is an adversary holding the transmitted 64-d
latents, not model weights or training data. Report the full privacy-utility
curve rather than a single point, because a single point invites the reader to
assume the rest of the curve is favourable.

**Validating metric.** identity re-identification rate vs chance; LPIPS on reconstructions; utility at each privacy setting

**Gate.** re-identification not above chance

**The interface may say.** "Transmitted representations were tested for identity recovery. See the report."

## Layer 2 — Analysis

### `analysis.phase_detection` — Phase detection

**synthetic** · owner: Marium · blocked on: labels

- *method*: Farha & Gall (2019). MS-TCN: Multi-Stage Temporal Convolutional Network for Action Segmentation (CVPR 2019)  ← venue unverified
- *method*: Yi, Wen, Jiang (2021). ASFormer: Transformer for Action Segmentation (BMVC 2021)  ← venue unverified

**What we take.** Temporal action segmentation. MS-TCN++ as the model, including the
truncated-MSE smoothing loss over log-probs, and the field's standard reporting
protocol: F1@{10,25,50}, edit score, MoF. ASFormer as a second model if time
allows.

**What we change.** Six phase classes over a 40-minute sequence rather than kitchen
activities over a few minutes. Leave-one-subject-out cross-validation, because
at n around 45 anything else leaks subject identity and inflates every number.
Current code ships a windowed RandomForest as a stand-in; the metrics, LOSO loop
and graph logic only consume (y_true, y_pred) and do not care which model
produced them.

**Validating metric.** F1@{10,25,50}, edit score, MoF, per-class recall, LOSO

**Gate.** per-class recall reported for all six phases, not just MoF

**The interface may say.** "Session segmented into problem-solving phases."

### `analysis.long_tail` — Rare-phase handling

**spec** · owner: Marium · blocked on: labels

- *method*: Menon et al. (2021). Long-tail learning via logit adjustment (ICLR 2021)  ← venue unverified
- *fallback*: Cui, Jia, Lin, Song, Belongie (2019). Class-Balanced Loss Based on Effective Number of Samples (CVPR 2019)  ← venue unverified

**What we take.** Group-wise logit adjustment, or class-balanced focal loss as the fallback.

**What we change.** The class distribution is brutally skewed toward Execution, and
Recovery and Verification are both rare and the diagnostically interesting ones.
That inversion is the motivation paragraph, not a caveat.

**Validating metric.** per-class recall on Recovery and Verification

**Gate.** rare-class recall within 15 points of Execution recall

### `analysis.process_graph` — Process graph

**synthetic** · owner: Marium · blocked on: labels; blind quality ratings

- *formalism*: van der Aalst. Process Mining: Data Science in Action (Springer (book))  ← venue unverified

**What we take.** Directly-follows graphs from process mining, via pm4py. Nodes are
phases, edges carry transition counts and mean originating-phase duration.
Brings traces, conformance checking and trace clustering along at no cost.

**What we change.** Graph features (n_transitions, cycle_count, phase_entropy,
backtrack_ratio) are tested against scalar baselines (total time, edit count)
for predicting blind-rated solution quality. If the graph does not beat the
scalars, it is decoration.

**Validating metric.** graph-structural features vs scalar features, predicting blind-rated quality

**Gate.** graph features beat scalars, or the graph is descriptive only

**The interface may say.** "Visualisation of the observed phase transitions."

### `analysis.fusion` — Multi-encoder fusion

**spec** · owner: Marium · blocked on: labels

- *architecture*: Cheng et al. (2024). Emotion-LLaMA: Multimodal Emotion Recognition and Reasoning with Instruction Tuning (NeurIPS 2024)

**What we take.** Multi-encoder-to-shared-embedding fusion for combining event features
and webcam features into one representation, following the architecture that
fused audio, three visual encoders and text into a language backbone.

**What we change.** Their weakest categories were the rare and ambiguous ones even
with a purpose-built 33k-sample dataset. ProblemProof's target states are
exactly that category, on two orders of magnitude less data. Assume the
weakness transfers and measure it rather than hoping.

**Validating metric.** weighted and unweighted average recall, per state

**Gate.** UAR reported alongside WAR so rare states cannot hide

### `analysis.segment_gate` — Expensive-scoring attention gate

**spec** · owner: Marium · blocked on: analysis.phase_detection

- *method*: Cheng et al. (2024). Emotion-LLaMA (NeurIPS 2024)

**What we take.** A cheap pre-filter that selects behaviourally significant windows, in
the spirit of Action-Unit-peak selection, so the expensive encoder and the
scoring pipeline do not run uniformly across a 40-minute session.

**What we change.** The peak signal is behavioural (pause, app switch, keystroke
burst) rather than facial AU intensity, because the AU route reintroduces the
affect-inference problem this system avoids elsewhere.

**Validating metric.** FLOPs saved vs F1 retained

**Gate.** no F1 loss beyond 2 points at >= 50% compute saved

### `analysis.delegation_ratio` — Delegation ratio and AI-provenance metrics

**synthetic** · owner: Amatul · blocked on: the silent-zero fix; artifact upload path; a decision on the desktop agent; then real sessions

**What we take.** delegation_ratio: AI-origin characters in the final artifact over
total characters. Computed alongside observed_ai_fraction,
external_ai_fraction/external_ai_seconds, and verified_accepts/
unverified_accepts — all derived from the same accept/reject/verify event
stream as verification_latency.

**What we change.** No prior work defines this metric because it presupposes an
LLM-assisted workflow no pre-2023 corpus has. It is named explicitly in the
research plan alongside verification_latency but was not given its own
registry entry when that one was written — found live and computed on real
captured events, with no gate on the field, by the Job 1 code audit rather than
by design.

Two defects found by the instrumentation audit, both open:

(1) Silent zero. compute_delegation_ratio sums char_count over
ai_output_accepted events for its numerator; with no accepts the numerator is 0
and the None guard fires only on a falsy denominator, so a real artifact plus
zero accepts yields 0.0. That is indistinguishable from a participant who
genuinely wrote everything themselves. external_ai_seconds has the same defect
and is worse in kind: it lands 0.0 in the same manifest dict three lines above
external_ai_fraction: None, so one underlying fact gets two encodings side by
side. verification_latency, observed_ai_fraction and external_ai_fraction all
correctly return None. Two of five are wrong, and they are the two a reader
would quote.

(2) No server-side denominator. The final artifact is saved to localStorage and
never uploaded, so compute_delegation_ratio has no server-side caller and
cannot get one as written. derive_ai_metrics is called only from the desktop
agent, which no participant is instructed to run.

**Validating metric.** correlation with blind-rated solution quality and with verification_latency

**Gate.** released alongside analysis.verification_latency once both have real-session validation

**The interface may say.** "Share of the final artifact that originated from AI output the participant accepted."

### `analysis.verification_latency` — Verification latency metric

**synthetic** · owner: Amatul · blocked on: real sessions; blind quality ratings

**What we take.** Nothing. This metric does not exist in prior work because it could not.

**What we change.** Defined as t(first verification_action) - t(ai_output_accepted).
Every existing corpus of human problem-solving process predates LLM assistants,
so there is no prior baseline to compare against. Tested against time-on-task,
total edits and AI call count for predicting solution correctness.

**Validating metric.** Spearman rho vs blind-rated correctness; logistic regression vs baselines

**Gate.** beats time-on-task at predicting correctness

**The interface may say.** "Time between accepting AI output and first checking it."

### `profile.analyze_then_judge` — Evidence-first scoring

**spec** · owner: unassigned · blocked on: labels; validator rubric

- *method*: R-PRM: Reasoning-Driven Process Reward Modeling (EMNLP 2025 (Main))

**What we take.** Write a full analysis of each phase, checking it against prior
phases, before emitting any judgment. The evidence trail is produced first and
the number second, never the reverse.

**What we change.** Their experiments were entirely on mathematical reasoning where
each step is objectively right or wrong. ProblemProof has no ground truth per
phase, so the analysis is the deliverable and the number is secondary. Their
threshold-stability finding is the part to replicate, because these scores get
used at cutoffs by people who did not read the methodology.

**Validating metric.** first-driver identification accuracy; threshold robustness across cutoffs

**Gate.** score ordering stable across at least three cutoff choices

**The interface may say.** "Written evidence for each phase, with the score it supports."

### `profile.metric_rubric` — Four-part metric rubric

**spec** · owner: unassigned · blocked on: profile.analyze_then_judge

- *taxonomy*: Evaluating Step-by-step Reasoning Traces: A Survey (EMNLP 2025 (Findings))

**What we take.** Factuality, validity, coherence, utility applied to every process
metric, instead of one opaque number.

**What we change.** The survey's open problem is that defining a single reasoning
step is unresolved and depends on model, problem and evaluator. ProblemProof
answers that with behavioural segmentation (pauses, app switches, keystroke
bursts) rather than semantic parsing, which is a contribution to the survey's
open question rather than a workaround.

**Validating metric.** rubric applied per metric; disagreement rate between raters per axis

**Gate.** no metric ships without all four axes assessed

### `profile.judge_consistency` — Scoring-engine self-consistency

**spec** · owner: unassigned · blocked on: profile.analyze_then_judge

- *measurement*: Rating Roulette: Self-Inconsistency in LLM-As-A-Judge Frameworks (EMNLP 2025 (Findings))

**What we take.** Repeated identical judgments on the same input, reporting the
standard deviation, split subjective vs objective metrics.

**What we change.** None needed. This is cheap to implement, almost nobody does it,
and it catches a reliability problem that exists independently of any bias
problem. Run it before trusting a single profile.

**Validating metric.** repeated-judgment SD per metric, subjective and objective separately

**Gate.** subjective-metric SD below the reliability threshold, or the metric is cut

### `profile.label_routing` — Hybrid label routing

**spec** · owner: unassigned · blocked on: labels

- *method*: The Lessons of Developing Process Reward Models in Mathematical Reasoning (ACL 2025 (Findings))

**What we take.** Cheap heuristic labelling for unambiguous segments, expensive human
or judge labelling reserved for ambiguous ones.

**What we change.** Their finding is that cheap Monte-Carlo labelling produces worse
and less generalisable models than judge or human annotation. That is the
justification for spending scarce human hours only where the routing says they
are needed, and it is also a warning against routing too aggressively.

**Validating metric.** agreement between routed labels and full human annotation on a held-out slice

**Gate.** routed labels within 5 points of full-human kappa

### `calibration.euclidean_alignment` — Personal baseline alignment

**synthetic** · owner: Tasfiah · blocked on: real calibration sessions

- *method*: He & Wu (2020). Transfer Learning for Brain-Computer Interfaces: A Euclidean Space Data Alignment Approach (IEEE TBME 67(2))  ← venue unverified
- *metric*: Shrout & Fleiss (1979). Intraclass correlations: Uses in assessing rater reliability (Psychological Bulletin)  ← venue unverified

**What we take.** Euclidean Alignment, the standard cross-subject transfer baseline
from BCI: per-subject covariance of calibration features, whiten by the inverse
square root of the mean covariance, apply the same transform to session
features.

**What we change.** Webcam and event features rather than EEG. A three-task
calibration battery feeds it, and the third task (a trivially easy problem)
matters most because it separates 'types slowly' from 'thinking hard'. Do not
invent a normalisation scheme here.

**Validating metric.** ICC(2,1) per feature pre/post; variance decomposition subject/task/residual; downstream F1 with and without

**Gate.** subject variance drops AND downstream F1 does not

**The interface may say.** "Signals are compared against this person's own baseline."

### `fairness.bias_measurement` — Level bias and spread bias

**spec** · owner: Tasfiah · blocked on: real sessions across groups

- *framework*: JobFair: A Framework for Benchmarking Gender Hiring Bias in Large Language Models (EMNLP 2024 (Findings))

**What we take.** Level Bias (differences in average outcome) and Spread Bias
(differences in score variability), measured with permutation testing rather
than a pass/fail threshold, across every archetype and demographic group.

**What we change.** Their overdebiasing result is the live risk here: correction that
overshoots creates a new bias in the opposite direction. Applied to a personal
baseline calibration layer this is not hypothetical. Alignment that removes all
between-person variance is not fairness, it is signal destruction, and both
numbers have to be reported together for that to be visible.

**Validating metric.** level bias, spread bias, max group gap across expressiveness terciles

**Gate.** gap shrinks post-alignment AND task variance is preserved

### `fairness.input_firewall` — Appearance input firewall

**spec** · owner: Tasfiah · blocked on: profile.analyze_then_judge

- *measurement*: Blinded by Context: Unveiling the Halo Effect of MLLM in AI Hiring (ACL 2025 (Findings))

**What we take.** The halo-effect measurement: image-based supplementary information
shifts unrelated judgments more than the same information given as text.

**What we change.** They diagnose the failure mode and propose no system-level fix.
The fix here is architectural, since the scoring model receives features and
never pixels. The halo delta between a features-only condition and a
features-plus-appearance condition is how that gets proven rather than
asserted.

**Validating metric.** score delta, features-only vs features-plus-appearance-metadata

**Gate.** delta not distinguishable from zero

**The interface may say.** "The scoring model never receives face video or appearance data."

## Layer 4 — Human validation

### `validation.cued_recall` — Cued retrospective labelling protocol

**synthetic** · owner: shared · blocked on: a real session for a real participant to narrate

- *protocol*: van Gog, Paas, van Merriënboer, Witte (2005). Uncovering the problem-solving process: cued retrospective reporting (Journal of Experimental Psychology: Applied)  ← venue unverified

**What we take.** Cued retrospective reporting: the participant narrates their own
recorded session afterwards, prompted by the recording rather than by a
researcher's questions.

**What we change.** Applied to phase labelling rather than think-aloud analysis. This
is what makes the labels participant-derived rather than researcher-imposed,
which matters because the phase taxonomy is the thing under test. Implemented
as pause-triggered prompts with a 60s fallback so no stretch goes unreported,
converted to labels.py's tiled segment contract by construction — each
segment's boundary comes directly from the adjacent point, so gaps cannot occur
mid-sequence. The real failure mode is the tail (a pass stopping before the
recording ends), which is caught by labels.py's existing rule and tested
explicitly. `synthetic` here means the same thing it means for
validation.kappa_gate: a real, non-placeholder implementation exercised so far
against hand-written test fixtures, not yet against a real participant
narrating a real recording.

**Validating metric.** coverage of session duration; disagreement with expert annotators

**Gate.** coverage >= 95% of session duration on real sessions

**The interface may say.** "Segments are the participant's own account of their process, given while watching the recording."

### `validation.kappa_gate` — Inter-rater reliability gate

**synthetic** · owner: shared · blocked on: validation.cued_recall; annotators

**What we take.** Cohen's kappa for two annotators; Krippendorff's alpha beyond two.

**What we change.** Enforced structurally rather than procedurally. Labels are stored
one file per source so two annotators can never overwrite each other, and the
tiling rule is enforced on write because a shared gap reads as agreement on
Understanding and would inflate kappa with agreement nobody expressed.
Implementation (reliability.py) is complete and correct, not a placeholder —
confusion matrix, top-confusion reporting, a CLI that exits non-zero on a
failed gate. `synthetic` here means only what it means everywhere else in this
file: exercised so far against hand-written test fixtures, not against a real
two-annotator label pair, because no annotators have labelled a real session
yet.

**Validating metric.** Cohen's kappa between expert_a and expert_b, per phase

**Gate.** kappa above threshold, or the phase taxonomy is revised before modelling

### `validation.organization_review` — Organisational validation lifecycle (RQ7)

**stub** · owner: shared · blocked on: Real reviewers at real organisations. Every number in the metric
is a property of humans doing reviews, and zero reviews have happened. The
machinery is implemented and tested; a lifecycle that has never carried a real
decision has measured nothing about reviewers.

**What we take.** A four-state one-way lifecycle — participant_submitted →
organization_review → validated → performance_released — with the reviewed
annotation frozen into an immutable, content-hashed version at the moment
review opens. A revision creates a new version; the original is never
rewritten. `validation.json` records the organisation, the reviewer, the
annotation version, the decision, the severity, the notes and the evidence
references. Every consequential action is appended to an audit log, including
a reviewer's evidence access.

**What we change.** Three deliberate choices, each a place where the obvious
implementation says something untrue.

A `disputed` decision does NOT move the session to `validated`. A disputed
record has not been validated by anybody, and `is_validated` is what Layer 3
reads before assembling a participant-facing profile.

A revision request does NOT move the state backwards. It is the same review
continuing against a record that is about to change, not the session leaving
the organisation, and a queue somebody works from has to be right about where
work is.

Severity is computed server-side and only server-side. The frontend previews it
before submission — Frontend Spec 7.2, a reviewer must never discover the
consequence of their action afterwards — but a client that could name its own
severity could file a full dispute as a minor note.

Organisation review and the two blinded expert passes do not read each other.
The expert passes evaluate the taxonomy; organisation review controls
participant-facing release. An organisation shown the inter-rater agreement is
reading a research diagnostic as a candidate's quality score, and an expert
pass that knew a session was already confirmed is no longer independent.
Enforced structurally by an AST-level test in both directions.

**Validating metric.** reviewer agreement on sessions independently reviewed twice; review
turnaround from submission to decision; annotation-revision rate (share of
reviews that request a revision, and how many versions a session accumulates)

**Gate.** reviewer agreement (Cohen's kappa on the confirm/adjust/dispute decision) >= 0.6 across independently double-reviewed sessions, with the revision rate reported alongside

**The interface may say.** "Validated by {organisation}, against annotation version {n}."

### `identity.face_match` — Face-match identity continuity

**synthetic** · owner: unassigned · blocked on: shadow-mode scores across groups; liveness detection; Art. 9 legal review

**What we take.** A face-recognition embedding as the identity oracle, cosine
similarity as the comparison, and two thresholds rather than one: strict at
calibration where a false stop costs minutes, lenient mid-exam where a false
flag accuses a person. Enrolment from a live capture only; the embedding is
computed and held client-side and only a score reaches the server.

**What we change.** The matcher is REAL and RUNS — MediaPipe FaceDetector for locating
and cropping, ONNX Runtime Web for the embedding — and ships in SHADOW mode: it
computes scores and records them, and is structurally unable to refuse entry or
raise a flag. `assertUsable` rejects enforced-while-unvalidated on both client
and server, and the server checks its own enforcement level rather than
trusting the outcome the client reported.

Shadow exists because the alternative is circular. Per-cohort thresholds cannot
be fitted without real scores, and real scores cannot be collected without
running the matcher, so 'wait until validated' forbids the only activity that
could end the wait. Shadow produces exactly the measurements the validation
study needs while remaining incapable of acting on them. Shadow results do not
raise the assurance level, because a credential claiming L2 on a check nobody
was allowed to act on is the misleading disclosure §4.2 warns about.

Status is `synthetic` rather than `pilot`: the pipeline runs end to end and has
been exercised only against constructed cases. It reaches `pilot` when the
per-cohort error rates below have been measured on real sessions.

Recognition weights are deliberately not bundled. A model's demographic error
profile is a property of its weights and is exactly what is unmeasured here;
NIST FRVT reports rates for named algorithms, and an unattributed ONNX has no
published characteristics at all. See docs/identity-model-setup.md.

Two blockers remain that are not engineering tasks: no liveness detection
exists, so enrolment is 'live camera' but not 'verified live'; and whether
adding identity matching as a processing purpose makes the already-stored
webcam video Art. 9 data needs legal review.

**Validating metric.** per-cohort false-match and false-non-match rates at both thresholds; disparity ratio across cohorts

**Gate.** per-cohort error rates measured from shadow-mode scores and disparity within an agreed bound; liveness detection in place

### `authenticity.process_authenticity_score` — Process Authenticity score

**REJECTED** · owner: unassigned · blocked on: a dataset that does not exist

- *probe architecture*: Face-Focused Cross-Stream Network for Deception Detection in Videos (CVPR 2019)
- *probe dataset*: DOLOS: Audio-Visual Deception Detection dataset (ICCV 2023)

**What we take.** A cross-stream network correlating face and body-motion streams
jointly rather than fusing them independently, trained with meta-learning to
cope with scarce deceptive data.

**Why not.** Rejected for the credential path in v1. The nearest precedent is
104 courtroom videos from 58 subjects in a narrow high-stakes lie domain; the
largest public alternative is 1,675 gameshow clips. Neither transfers to 'is
this person genuinely thinking or performing thinking across 40 minutes of
work'. The full-system document asserts that genuine deep thinking produces
micro-signals that are not consciously controllable; the literature does not
support that claim at consumer webcam quality, and shipping a score built on it
would be the one place where ProblemProof contradicts its own evidence base.
Build the architecture as a research probe against DOLOS, report what it does,
keep it out of the credential.

**Validating metric.** AUC on DOLOS, reported as a probe result only

**Gate.** never promoted above `spec` without a purpose-built dataset

### `authenticity.cognitive_load_inference` — Cognitive load inference from webcam

**REJECTED** · owner: unassigned · blocked on: n/a

- *constraint*: Barrett et al. (2019). Emotional Expressions Reconsidered (Psychological Science in the Public Interest 20(1))  ← venue unverified

**What we take.** n/a

**Why not.** Rejected. The full-system document describes gaze patterns, blink
rate and micro-expression change as cognitive load signals. Pupillometry has
support under controlled lighting with calibrated equipment; a laptop webcam in
an uncontrolled room is neither. Emit the raw signals, let the segmentation
model use them if they carry information, and make no claim about load.
